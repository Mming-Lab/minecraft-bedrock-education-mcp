# 読む前に

**この文書だけで実装を始められるように書いてある。** 会話の文脈は前提にしない。

数値はすべて **Minecraft Education 1.26.3200（日本語クライアント、Windows）での実測**。
推測と実測を混ぜないため、未測定のものは「未測定」と明記する。

---

# 1. 決まったこと

## 1.1 ワールドを読む方法：アドオン（Script API ブリッジ）が主、ワールドDBが従

| 経路 | 1ブロック | 4096ブロック | ブロック状態 | エンティティ | 同一PC |
|---|---|---|---|---|---|
| **アドオン** | **171ms** | **3,706ms** | **取れる** | **取れる** | **不要** |
| ワールドDB | 2〜7秒 | 2〜7秒 | 取れる | 実質不可 | **必須** |
| コマンド（`testforblock`等） | 96ms | 約33秒 | 取れない | 不可 | 不要 |

**アドオンが速く、情報量も多い。** DBが勝つのは2点だけ：

- **アドオンから見えない領域**（`getBlock` は読み込み済みチャンクしか返さない）
- **アドオンを導入できない環境**

`testforblock` は使わない。**日本語クライアントでは `statusMessage` もブロック名も翻訳される**
（`ダイヤモンドブロック`）ので、正規表現では解けない。

## 1.2 通信方式

```
MCP → /scriptevent mcp:<action> <id> <json>      既存のWebSocket
      ↓ アドオンのスクリプト
MCP ← player.runCommand('tell @s MCPB|<id>|<json>')  → PlayerMessage イベント
```

**往復ともWebSocket。ファイルもDBも経由しない。**

## 1.3 却下したもの（すべて理由付き）

| 案 | 却下理由 |
|---|---|
| `@minecraft/server-net`（HTTP） | 公式ドキュメント：**専用サーバ限定。ゲームクライアントでは機能しない** |
| `world.sendMessage` | **WSの `PlayerMessage` を発火しない**（実測）。ゲーム内には表示される |
| `dimension.runCommand` | 1.8.0 時代に存在しない。`player.runCommand` を使う |
| 動的プロパティ → DB | DB直読みと同じファイル・同じ待ち時間で、アドオン依存が増えるだけ |
| ファイル／パイプ／シリアル | Script API にAPIが存在しない |
| `/hud @s hide chat` | **`chat` は要素名に無い**（実測で列挙） |
| `say` | 全員にブロードキャスト。`tell` が同性能で私信 |

# 2. 実測値（実装が依存する定数）

## 2.1 アドオン

| 項目 | 値 | 備考 |
|---|---|---|
| `@minecraft/server` | **`2.1.0`** | 1.7.0〜2.0.0 は**全て無応答**。14種を並べて確認 |
| `min_engine_version` | **無関係** | 1.18.30 / 1.21.0 の両方で動作 |
| 出力経路 | **`player.runCommand('tell @s ...')`** | **ソースは `tell`。実機に入っているパックは `say` の古い版**（下記） |
| **1行の上限** | **到達した最長：`say` 512文字 / `tell` 505文字** | **超過した行は丸ごと消える**（切り詰めではない） |
| 行数の上限 | **観測されず** | 200行連続で欠落0 |
| 1ブロック | 171ms（中央値、10回。125〜235） | |
| 4096ブロック（16³） | 3,706ms / 172行 / 欠落0 | `perMessage: 24` |
| 256ブロック（8×4×8） | 1.7〜1.8秒 | `perMessage` 8〜64 で変化なし。往復の固定費が支配的 |

**`MAX_LINE = 460` を使う**（到達実績505に対する余裕）。超過が「丸ごと消える」ため外し方が高くつく。

## 2.1.1 行長の境界（2026-08-25、`d2-channel` で刻み5の掃引）

| アドオンが送る text | `say` の到達長 | `tell` の到達長 |
|---|---|---|
| 504 / 505 | **512（届く）** | **505（届く）** |
| 514 / 515 | **消える** | **消える** |

`say` と `tell` はコマンド接頭辞の長さが違う（`say ` = 4、`tell @s ` = 8）ので、
**上限が「テキスト長」で決まるのか「コマンド全長」で決まるのかは分離できていない。**
どちらでも受信側で観測される安全上限は **505**。460 はその下に 45 文字の余裕を残す。

**`MAX_LINE` を上げる理由は無い。** 実測で `perMessage` を 8 から 64 まで振っても所要時間は
1.7〜1.8秒で変わらない（往復の固定費が支配的で、行数は効かない）。行を長くしても速くならず、
外したときの損失だけが大きい。

## 2.1.2 取りこぼしの検出は実機で効く（2026-08-25、`d1-bridge`）

256ブロックの領域を `perMessage` 8/16/24/32/48/64/96/160 で読んだ結果：

| `perMessage` | 結果 | 最長行 |
|---|---|---|
| 8〜64 | **完全**（256/256） | 100 → 457 |
| 96 | **不完全として拒否**（3パート中2欠落） | 453 |
| 160 | **不完全として拒否**（2パート中2欠落） | 99（ヘッダのみ） |

**「短いのに受理された」ケースはゼロ。** ヘッダの `parts` と実到着数の照合が、
実機で起きる取りこぼしを実際に捕まえる。これがこのプロトコル層の存在理由そのもの。

**`itemsPerLine` の推奨値は当てにしすぎない。** この領域は `air`/`stone`/`dirt` しか無く
平均3.3文字だったため 57 を推奨したが、`polished_deepslate_bricks`（25文字）が並ぶ領域では
同じ 57 が確実に消える。**読む前にブロック名の長さは分からない。**
取りこぼしは確実に検出できるのだから、**拒否されたら `perMessage` を半分にして再試行**する。

## 2.2 ワールドDB

| 項目 | 値 |
|---|---|
| ブロック配置後のフラッシュ | **約25秒**（自動セーブ待ち） |
| `structure save` によるフラッシュ強制 | **2.1 / 6.6 / 5.2 秒**（3回測定） |
| DBスナップショット | 約60ms（このワールドで107KiB） |
| DBのロック | **原本は排他ロック。`FileShare.ReadWrite` でコピーしてから開く** |
| サブチャンクのインデックス順 | **x → z → y** |
| 構造物のインデックス順 | **x → y → z**（サブチャンクと違う） |
| 高さの符号化（`getchunkdata`） | `y = バイト値 − 255` |
| `fill` の体積上限 | **32768**（ゲーム自身が `33792 > 32768` と返答） |

## 2.3 コマンド

| 項目 | 値 |
|---|---|
| `execute if block` の並列 | **100本同時で774ms、失敗0** |
| キャレット `^` | **受理される** |
| `statusCode < 0` | **「拒否」を意味しない**（後述） |

# 4. これから作るもの

## 4.1 トランスポート層（最優先）

`bridge/client.ts` は `BridgeTransport` を注入で受け取る。**その実装がまだ無い。**

```ts
interface BridgeTransport {
  send(commandLine: string): Promise<void>;
  onChat(listener: (message: string) => void): () => void;
}
```

socket-be の上に作る（D-2：SocketBEフォーク）。**注意点：**

- **`ServerEvent.PlayerMessage` のハンドラを接続前に登録すること。**
  socket-be はサーバに登録されたハンドラを見て購読を決めるので、
  接続後に登録しても購読されない。**これで1セッション失った。**
- 暗号化は `disableEncryption` でゲーム側の設定に合わせる

## 4.2 MCPツール

| ツール | 経路 | 備考 |
|---|---|---|
| `world.get_block` | アドオン | 171ms。状態付き |
| `world.read_region` | アドオン | 4096ブロック/3.7秒。**未読み込みチャンクは `null`** |
| `world.entities` | アドオン | |
| `world.container` | アドオン | |
| `world.read_region_offline` | DB | 未読み込み領域・アドオン不在時 |

**`readregion` の `perMessage` は呼び出し側が決める。**
`itemsPerLine(idLength, averageItemChars)` が `protocol.ts` にある。
ブロック名の長さが読むまで分からないので、**低めに見積もる**
（低すぎれば行が増えるだけ、高すぎれば行が丸ごと消える）。

## 4.3 アドオンの配布

現在 `tools/mcp-bridge/` は検証用の置き場。配布時に：

- `bench` / `channel` ハンドラを削除
- `.mcaddon` として同梱するか、導入手順を書く
- 導入先は `development_behavior_packs/` か、ワールドの `behavior_packs/`
- **`world_behavior_packs.json` に書けば有効化できる**（ゲームが受理して整形し直す）
- **パックフォルダはアプリ起動時に走査される。** 追加後はゲームの完全再起動が要る

# 5. 実装で踏むと分かりにくい罠

## 5.0 ソースを直しても、ワールドの中で動いているのは古いパック

**2026-08-25 に実機で確認：この文書が「`tell` を選んだ」と書いている一方、
ワールドに入っているパックは `CHANNEL = 'say'` の版だった。**

判定は対照で取った（`d2-channel`）。`channel` ハンドラが同じ文字列を両経路で送り、
受信側で接頭辞を比べる：

| 経路 | 到着形 |
|---|---|
| `say` | `[Kai_U] MCPB\|cc.say\|yyy…` — **名前の接頭辞あり** |
| `tell` | `MCPB\|cc.tell\|yyy…` — **接頭辞なし** |
| `ping` の返答 | `[Kai_U] MCPB\|pg\|{…}` — **接頭辞あり ＝ `say` 経路** |

つまり **「`tell` にしたので教室の全員には見えない」という帰結は、実機ではまだ成立していない。**
パックフォルダはアプリ起動時にしか走査されない（§4.3）ので、ファイルを置き換えても
**ゲームを完全再起動するまで古いスクリプトが動き続ける。**

実装はこれにブロックされない（`parseLine` は接頭辞の有無を両方受ける）。
**成立していないのは配布側の前提だけ**だが、それを「直した」と言い続けるのが §6 の形そのもの。

## 5.1 `statusCode < 0` は「拒否」ではない

| メッセージ | 実際 |
|---|---|
| `0 個のブロックで満たしました` | **成功**。置換対象が0個だっただけ |
| `そのブロックは設置できません` | **既に同じブロックがある** |

**負のコードを一律エラー扱いすると、成功した `fill` を失敗と報告する。**
コーパス17本のうち「拒否」に見えた8本で、本物の構文エラーは1本だけだった。

**`setblock` は冪等でない。** 同じブロックを2回置くと2回目が負のコードを返す。

## 5.2 応答の取りこぼしは見えない

行が1本落ちても、**残りは全部正常なJSON**。外からは短い答えと区別が付かない。
ヘッダの `parts` と実到着数を照合すること（`assemble()` が実装済み）。

これが無いと、**一部しか見ていない領域を「見た」としてAIに渡すことになる。**

## 5.3 「見えない」と「無い」を混同しない

`getBlock` はチャンク未読み込み時に `undefined` を返す。これは `air` とは別物。
同一視すると、**見ていない空間を見たとAIに信じさせる。**

構造物の未記録位置（インデックス `-1`）も同じ。`air` は「見て空気だった」、
`null` は「保存が飛ばした」。

## 5.4 プレイヤーが存在してから話す

`player.runCommand` はプレイヤーが要る。**起動直後の tick では存在しない。**
`system.runTimeout(fn, 60)` 以降で。

## 5.5 ワールドDBは必ずコピーしてから開く

原本は排他ロック。`FileShare.ReadWrite` で読み、`LOCK` ファイルを除外してコピーする。

# 6. この調査で4回繰り返した誤り

**すべて「前提が成立していないのに結論を出した」もの。** 実装中も同じ形で踏みうる。

| # | 内容 | 実際 |
|---|---|---|
| 1 | `agent inspect` が無反応 → socket-be が握り潰していると疑った | **フレーム自体が来ていなかった** |
| 2 | チャットに返事が無い → 機能が無いと判定 | **購読していなかった** |
| 3 | スクリプトが動かない（**3セッション**） | **動いていた。`world.sendMessage` がWSに乗らないだけ** |
| 4 | 「隠したまま届いた」と報告 | **隠れていなかった**（`hud` が構文エラー） |

**対策：判定の前に対照を取る。**
「返事が無い」と言う前に、その経路で**返事が来ることを別途確認する**。
「効いた」と言う前に、**条件が成立したことを確認する**。

リグは4系統の独立した信号（`sendMessage` / `runCommand(say)` / ブロック配置 / 動的プロパティ）
を出す形にしてある。1つの経路だけを見て判定しない。

# 7. 未測定・未解決

| 項目 | 影響 |
|---|---|
| `/reload` が動的生成した `.mcfunction` を拾うか | 書き込みの一括化（1往復1000ブロック）が可能かどうか |
| `tell` を隠す方法 | ブリッジが使う1人の画面には172行流れる。**他の生徒には見えない** |
| DBからのエンティティ読み出し | アドオン不在時にエンティティが取れない |
| `getchunkdata` の色→ブロック対応表 | 陰影の正規化が要る。優先度低（アドオンが主なので） |
| アドオンの導入手順の自動化 | 教室で配る際の手間 |
| `leveldb-zlib` のプリビルド対応プラットフォーム | **npx配布（D-9）に影響する。ネイティブモジュール** |
