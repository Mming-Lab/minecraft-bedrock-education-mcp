# 結論：3層構造

**単一の方法では成立しない。** 実測の結果、それぞれに明確な守備範囲と限界がある。

| 層 | コマンド | 得られるもの | 1コマンドあたり | 限界 |
|---|---|---|---|---|
| **広域** | `getchunkdata` | **256列の高さ**（正確）＋表面色（陰影込み） | 16×16列 | 色→ブロックは非可逆 |
| **表面** | `gettopsolidblock` | **正確なブロック名**＋座標 | 1列 | 地表のみ |
| **任意点** | `execute if block` | 指定座標の一致判定 | 1座標 | 候補を当てにいく形 |

補助：`getchunks <dim>` で読み込み済みチャンク一覧、`querytarget @s` でプレイヤー位置。

**`testforblock` は使わない。** 日本語クライアントでは `statusMessage` が翻訳され、
ブロック名まで `ダイヤモンドブロック` になる。正規表現では解けない。

## 1. `getchunkdata` — 広域スキャン

```
getchunkdata <dimension: string> <chunkX: int> <chunkZ: int> <height: int>
```

**「与えた y より下で最初に見つかるブロック」の情報を、16×16=256列ぶん返す。**

### エンコーディング（実測で確定）

```
"S6J9wg*118,Qs3Xww,AAD/ww,0*14,PoRnwg,0*87,cHBwxA,0*13,cHBwyw*3,0*11"
```

- カンマ区切り。合計は必ず **256エントリ**
- `*N` は「**あとN個**」（N回ではない）。`AAAAAA*255` が256になる
- **6文字の base64** = 新規リテラル。デコードして4バイト
  - **先頭3バイト = 描画色**（陰影込み。後述）
  - **4バイト目 = 高さ**。**`y = バイト値 − 255`**
- **素の数値** = **辞書インデックス**（そのチャンクでリテラルが初出した順、0起点）

### 高さの検証（3点一致）

| バイト | 計算 | 実際のy |
|---|---|---|
| `c2` = 194 | 194−255 | **−61**（草の地表） |
| `c7` = 199 | 199−255 | **−56** |
| `cb` = 203 | 203−255 | **−52**（石柱の頂点） |

柱を20ブロック上げたとき、バイトも `c4`→`d6` とちょうど20増えた。

### `height` 引数の意味（実測）

| 与えたh | 返り値 | 解釈 |
|---|---|---|
| 320, 0 | `...cHBwyw...`（y=−52） | 地表より上：一番上のブロック |
| −56 | `...cHBwxw...`（y=**−56**） | **−56 で頭打ち**＝上から探して最初 |
| −61 | `S6J9wg*255` | 地表ちょうど：全列が草 |
| −64, −66, −81 | `/wD/QA*255` | **`ff 00 ff`＝マゼンタ、高さ64** |

`ff00ff` はテクスチャ欠損色。**「見つからなかった」の番兵値**。

### ★限界：色はブロックIDではない

```
S6J9wg  →  4b a2 7d c2   草、y=−61
PoRnwg  →  3e 84 67 c2   同じ草、同じ高さ、色だけ暗い（柱の影）
```

`3e8467` は `4ba27d` の約0.83倍。**陰影が乗るので、同じブロックが複数の値を取る。**
色から材質を当てるなら、明度で正規化した上で対応表を作る必要がある（要・別途較正）。

**高さは正確。色は目安。** これが `getchunkdata` の正しい使い方。

## 2. `gettopsolidblock` — 正確な表面

```
gettopsolidblock <x> <y> <z>
  → {"blockName":"grass_block","position":{"x":0,"y":-61,"z":-3},"statusCode":0}
```

**構造化されており、翻訳されない。** `草ブロック` ではなく `grass_block`。
`getchunkdata` で当たりを付けた地点の確認に使う。

---

## 3. `execute if block` — 任意座標

```
execute if block <x> <y> <z> <block> [states] run <command>
  一致    → statusCode 0、statusMessage なし
  不一致  → statusCode 負、"サブコマンド if block テストの実行に失敗しました。"
```

**散文を一切返さないので翻訳に影響されない。** 判定は statusCode だけ。

### スループット（実測）

| 並列数 | 所要 | 1本あたり | 失敗 |
|---|---|---|---|
| 直列20本 | 2,243ms | 112ms | 0 |
| 10本 | 110ms | 11ms | 0 |
| 50本 | 184ms | 4ms | 0 |
| **100本** | **774ms** | **8ms** | **0** |

**100本同時でタイムアウト0・エラー0。** 以前の調査にあった
「100本で `TooManyPendingRequests`」は、少なくともこの構成では再現しなかった。

逆算：16×16×16 = 4,096ブロックを個別確認しても約33秒。
`getchunkdata` があるので通常は不要だが、**退路として実用範囲**。
